# Incident Report: VRKM-962-3 Extraction & Diagnostic Correction

**Date**: 2026-08-14  
**Target**: `vrkm-962-3` (Origin size: 3,349,405,509 bytes, ~3.35 GB, 9 cut segments)  
**Status**: Resolved / Fully Recovered in Production  

---

## 1. Executive Summary

During extraction of 9 segments from `vrkm-962-3.mp4`, initial attempts using legacy/unauthenticated workflows failed for segments 05–09. Several unverified hypotheses were initially formed:
- URL expiration causing HTTP 416
- "Physical hole" in the remote file due to stalled cloud torrent download
- Impossibility of partial extraction

Rigorous diagnostic verification using authenticated transport disproved all corruption hypotheses. The actual root causes were:
1. Attempting extraction via anonymous CDN media links rather than the authenticated production transport.
2. A budget calculation bug (`estimate_origin_budget`) that pre-blocked extraction for moderate selection (~46%) due to headroom/overhead exceeding the 80% fuse before extraction began.

Following PR #26 (fixing budget calculation) and running the standard authenticated workflow (`python -m pikpak_llc.authenticated_workflow`), all 9 segments were successfully extracted and verified with 100% completion gate pass.

---

## 2. Timeline & Evidence

### 2.1. Initial Failure & Disproven Hypotheses
- Initial attempts encountered HTTP 416 on anonymous media links at byte offset `1,907,339,679`.
- Speculative conclusions that the file had a physical hole or was an incomplete torrent were disproven by the definitive authenticated test below.

### 2.2. Definitive Authenticated Range Test (A/B Control)
- Ran authenticated `rclone cat` with `--pikpak-no-media-link` on the same `vrkm-962-3` file:
  - `OFFSET 1,873,630,311`, `COUNT 65,536` -> **65,536 bytes transferred, EXIT_CODE: 0**
  - `OFFSET 1,907,339,679`, `COUNT 65,536` -> **65,536 bytes transferred, EXIT_CODE: 0**
- **Conclusion**: `PHYSICAL_HOLE_CLAIM=DISPROVEN`. The core object is complete on PikPak.

### 2.3. Pre-Block Budget Issue & Resolution
- Running the production authenticated workflow initially raised `BudgetConfirmationRequired`.
- The user selected 486.99s of ~1050s (~46.3% of video). With 2.0x headroom + 128MB overhead, the desired fuse reached 3.22 GB, exceeding `0.8 * 3.35 GB = 2.68 GB`.
- **Fix (Issue #25 / PR #26)**:
  - Changed budget semantics so `BudgetConfirmationRequired` is only raised when `estimated_selected_bytes >= hard_cap`.
  - When `estimated < hard_cap`, `max_origin_bytes` is clamped to `hard_cap` (aligned downward to rounding boundary).

## 4. Key Takeaways & Preventive Actions

1. **Strict Diagnostic Order**: Always follow the troubleshooting decision tree before jumping to infrastructure corruption conclusions.
2. **Authoritative Transport**: Never use anonymous media URLs to diagnose core file integrity; only authenticated direct storage ranges provide authoritative ground truth.
3. **Clean Worktree Isolation**: Operator tasks must run only from clean master; bug fixes and diagnostic experiments belong in isolated development worktrees.
